Method

How Codebase DNA reads a repository

A single scan tells you how a project looks today. It can't tell you whether it's getting better or worse, or why. Codebase DNA measures the same project at several points in its history, the same way every time, and explains the differences.

  1. Clone and read history

    The repository is cloned (blob-less, so only the files we actually check out are downloaded). We walk the first-parent history of the default branch.

  2. Pick the snapshots

    Up to eight commits, spread evenly from the first commit to the latest. When a tagged release sits close to one of those points, we use the release instead — “v2.0 vs v3.0” means more than two hashes. Re-running only analyses commits that are new.

  3. Measure every file

    Python is parsed with its own ast module. For JavaScript, TypeScript, Java, Go, Rust, C#, PHP and friends, comments and strings are blanked out and braces are matched to find each function. For each file we record lines of code, comments, functions, cyclomatic complexity, nesting depth, a maintainability index and TODO notes.

  4. Look at behaviour, not just code

    From git log we count how often each file changed in the 300 commits before the snapshot, and by how many people. A file's heat combines change frequency with complexity — the idea behind behavioural code analysis.

  5. Check for risk

    Pattern rules look for leaked credentials, eval, shell injection, SQL built from strings, disabled TLS checks, unsafe deserialisation and more. Dependency manifests are parsed to see what is pinned and what is known to be abandoned. Copy-pasted blocks are found by hashing every six-line window.

  6. Score and explain

    The measurements become six scores — the genes — and a weighted health score. Then a set of rules compares each snapshot with the one before (and with the very first) to write findings: what happened, why it matters, what to do. Findings are ranked so the most useful fix is first.

The six genes

GeneWeightBuilt from
Complexity20%Average cyclomatic complexity per function, share of functions above 10, deepest nesting.
Maintainability20%Maintainability index (Halstead volume, complexity, size, comments), duplication, very large files, very long functions.
Testing20%Lines of test code relative to source code, and whether CI runs them.
Security20%Risky patterns weighted by severity per thousand lines; any critical finding caps the score.
Dependencies10%Share of unpinned packages, known-risky packages, sheer number of dependencies.
Documentation10%README (and whether it says anything), comment density, licence.

Grades: A ≥ 85, B ≥ 70, C ≥ 55, D ≥ 40, E below.

What it is not

It isn't a compiler, a coverage tool or a vulnerability database. The numbers are heuristics, chosen to be consistent across snapshots, so a trend is meaningful even when an absolute number is debatable. Treat the findings as a well-informed colleague's opinion — a good place to start a conversation, not a verdict.
